# Phase 07 — Asset Seam

**Status:** Planned.
**Depends on:** [[Phase 03 - Legibility Tools]] (baked sprite output needs to be judged with the
tuning overlay available, not by rebuild-and-screenshot).
**Blocks:** [[Phase 09 - Placeholder Art]] — the placeholder art built in that phase should go
*through* this seam from the start, not be fused into the renderer and need retrofitting later.

## Why this phase

This is the architectural decision that makes the whole backbone framing real rather than aspirational.
The user is building the playable foundation while teammates design the game in parallel; they will
eventually hand over a real map, characters and assets. Two facts collide here: **zero external
files can ship** (no PNG, WAV, TTF, OGG, GLB — a hard contest rule, see [[Handover]] §1), and **the
team's art still has to get into the executable somehow.** The only legal path is a build-time bake:
authored art becomes a compiled-in C header, generated by a tool, committed to the repo, and never
loaded at runtime. This phase builds that pipeline and the seam that lets any drawable dispatch to
either a procedural routine or a baked sprite — so a teammate's asset replaces one named function,
not a hunt through the renderer.

The untracked `tree.glb` sitting at the vault root since before this framing existed is the exact
failure mode this phase prevents: someone assumed an asset file could just be dropped in and loaded.
It can't. This phase is what makes that possible in a way that still ships.

## Definition of done

- [ ] `tools/bake.ps1` reads `art/*.png`, produces `src/art_data.h` — indexed-palette (≤16 entries),
      RLE-encoded, with a per-sprite record of `{ w, h, anchor_x, anchor_y, pal_off, data_off }`.
- [ ] `src/art_data.h` is **committed to the repo**, so a clean build never requires running the bake
      tool — only regenerate it when art actually changes.
- [ ] A `draw_sprite` routine decodes and blits a baked sprite, respecting its anchor as the
      ground-contact point so it drops into the existing band-sweep depth sort correctly.
- [ ] Fog applies to a sprite's **palette**, once per sprite per reveal level — not per pixel — so
      `fog_lerp` remains the single path from true colour to screen colour without becoming a
      per-pixel-per-sprite cost.
- [ ] Every drawable that should eventually accept team art (`draw_tree`, `draw_building`,
      `draw_player` once it exists) goes through one named entry point that can dispatch to either
      the existing procedural routine or a baked sprite, controlled by a single flag or table entry
      — not a scattered set of call-site changes.
- [ ] `--sprite-test` exists: a round-trip test (encode a known image, decode it, confirm pixel-exact
      match), an anchor-placement test (a sprite's anchor lands on the correct tile), and a negative
      control (a corrupted RLE stream must be rejected, not silently misdrawn).
- [ ] Terrain, cliffs, and water remain procedural — this phase does not convert them to sprites,
      because they need to tile seamlessly and respond to per-tile elevation and fog in a way a
      fixed sprite can't.
- [ ] The byte cost of the first real baked sprite is measured and reported, turning "a 32×32
      indexed+RLE sprite costs ~200–600 bytes" from an estimate in [[Art Bible]] §8 into a fact.

## Concrete tasks

1. Write `tools/bake.ps1`: load a PNG (via .NET's `System.Drawing`, consistent with how this project
   already converts BMP screenshots to PNG — no new external dependency), quantize to an indexed
   palette per sprite, RLE-encode the index stream, emit the C header.
2. Decide and document the anchor convention concretely (bottom-centre for uprights, matching how
   `draw_tree` and `draw_building` already position themselves via `cx`/`by` — reuse that convention
   rather than inventing a new one) so a teammate authoring art has an unambiguous rule to follow.
3. Add `draw_sprite(fb, sprite_id, cx, by, rev)` near the other graphics primitives
   (`src/main.c`, the `fill_rect`/`iso_tile`/`fill_ellipse` cluster) with the same `(cx, by, rev)`
   signature shape as `draw_tree`/`draw_prop`, so callers don't need to know which kind of drawable
   they're calling.
4. Add the dispatch layer: for each candidate drawable, a single point (a lookup table keyed by
   variant, or a compile-time flag per category) decides procedural vs. baked. Document the contract
   in [[Art Bible]] §8 so it's discoverable without reading the renderer.
5. Write `--sprite-test` per the Definition of Done, following the existing negative-control pattern
   (`village_negative_test`, `solvable_negative_test`) for how corrupted input should be rejected.
6. Bake one real test sprite (even a placeholder shape) end to end, build, and report the measured
   byte delta.

## Verification gate

`--sprite-test` PASS including round-trip exactness, anchor placement, and the corrupt-stream
negative control. A build showing the measured byte cost of the first baked sprite. Visual
confirmation via screenshot that a baked sprite composites correctly into the existing depth sort
(appears in front of/behind the right neighbouring tiles and props).

## Traps specific to this phase

- **A sprite's fog has to be palette-level, not pixel-level, or it becomes the most expensive thing
  in the renderer for no visual benefit.** Every other surface in this codebase computes its fog
  blend per draw call already (`tile_colour` → `fog_lerp` once per tile, not per pixel); a sprite
  should follow the same shape — compute the faded palette once, then blit indices through it.
- **An RLE decoder is new code with a new class of off-by-one risk** (this project has hit exactly
  this class of bug before — the `sizeof`-on-a-decayed-pointer trap in [[Handover]] §7). Write the
  round-trip test *before* trusting the decoder with anything visual, and don't skip it because "it's
  just a bake tool."
- **The anchor convention needs to be right the first time**, because it becomes a contract a
  teammate authors art against. Changing it later means re-baking and potentially re-authoring
  everything upstream of it. Decide it deliberately (see task 2) rather than letting the first
  sprite's convenient placement become the de facto standard by accident.
- **`tools/bake.ps1` is a PowerShell script touching `src/main.c`-adjacent generated output** — the
  project's standing rule about never running `src/main.c` itself through a PowerShell text filter
  ([[Handover]] §7) doesn't directly apply to a *generated* header, but the same encoding caution
  (BOM, CP1252 vs UTF-8) applies to anything the bake tool writes. Write generated files with
  explicit UTF-8-no-BOM, or plain ASCII given it's just numeric arrays, and verify once by inspecting
  the output.
