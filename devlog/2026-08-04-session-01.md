**Start of the isometric pivot.** The team asked for a 2.5D isometric pixel-art look with layered
procedural art and a village world, replacing the flat top-down coloured-square renderer. This is
a change of rendering approach, which [[Agent Prompt]] names explicitly as requiring a flagged
decision rather than autonomous action — it was raised, three options were put, and the largest
was chosen deliberately. See [[Isometric Rendering]] and [[Village Generation]].

The size question was answered before any code was written: **bytes are not the constraint.** The
exe is 679,424 bytes of which 669,696 is SDL2 — every line of game logic written across Weeks 1–3
totals **9,728 bytes**, about 3.6 bytes per source line at `-Os`. The whole renderer plan is
estimated at +7 to +16 KB against 760,576 bytes of headroom.

## Slice 0 — The measurement that never existed

### Why this came first

[[Toolchain Setup]] and [[Handover]] both list "render cost of the tile loop not profiled" under
NOT verified, and the only performance number on record was **"56.2 fps"** from
[[2026-08-02-session-01]]. That number was never evidence of anything. The loop sleeps on purpose
to cap the frame rate, and `SDL_Delay` has millisecond granularity — `Sleep(14)` routinely returns
at 15–16 ms on Windows. The measurement was of sleeping, not of drawing.

Changing the renderer against an unmeasured baseline would have meant no way to tell whether the
new one was expensive. So: measure first, change nothing.

### Change

Four separate stopwatches per frame — **render**, **present**, **sleep**, **whole frame** — plus
pixel and call counters incremented inside `fill_rect` after clipping, so the count is real writes
rather than requested ones. Reported live in the window title with `--perf` (the only text channel
that exists before the Week 5 bitmap font) and as a summary on exit.

All of it sits behind `WAYFARER_PERF`, which defaults to `WAYFARER_SELFTEST`. The shipping binary
therefore contains **no** measurement code at all — the same structural argument as decision 8 in
[[Handover]]: "no debug code in the submission" should be a property of the build, not something
somebody has to remember. Both binaries run the identical render path, so numbers measured in one
apply to the other.

### Measured — 600 frames, seed 3, 640×360

```
render   mean   0.110 ms    max   0.341 ms
present  mean   0.127 ms
sleep    mean  16.534 ms    <- frame cap; SDL_Delay granularity lands here
frame    mean  16.851 ms    = 59.3 fps
pixels   mean    230544 /frame  = 1.00x the 230400-px screen
calls    mean       947 /frame
```

### What this settles

- **The "56 fps" was sleep, confirmed.** 16.534 ms of a 16.851 ms frame — **98.1%** — is spent
  inside `SDL_Delay`. The renderer was never the limiter and never came close to being it.
- **Render costs 0.110 ms of a 16.67 ms budget: 0.66%.** There is roughly **150× headroom** on the
  render path. The isometric renderer is projected at ~5.7× the pixel traffic of this one, which
  lands near 0.6 ms — still under 4% of budget. Performance is not a reason to compromise the look.
- **`pixels = 1.00× the screen` proves the flat loop has essentially zero overdraw**, which is why
  it never needed a screen clear. That property does not survive the isometric change: diamonds
  only tile the plane where the world exists, so a clear becomes mandatory in slice 1.
- **947 calls/frame** against ~1008 visible tiles — the difference is edge tiles clipped away.

### Not verified

- Measured on one machine, with the window unoccluded. `present` in particular is an OS blit whose
  cost depends on the compositor and window state; the 0.127 ms figure should not be treated as
  portable. It is a baseline for *comparison against later slices on this box*, which is what it is
  for.
- `--input-test` runs and reports cleanly, but with no external driver it sees no keys
  (`up=0 down=0 left=0 right=0`) and reports a zero position delta. Exercising the real key path
  needs the `PostMessage` harness described in [[Handover]]; that gets set up in the slice where
  input actually changes.

### Size

**679,424 bytes, delta +0.** The shipping binary is byte-identical to the pre-slice build, which
is the strongest available evidence that the instrumentation is genuinely absent from it.
Self-test build 696,832 bytes (not a deliverable, not budget-tracked).
