## Shape of the save

The world is a pure function of its seed, so the file is the seed plus the deltas play makes on
top of it — 28 bytes, flat, versioned, little-endian by hand (no struct dump, no padding, no host
endianness in the file): magic `WF`, version, seed, player x/y, abilities, shard mask, restored
mask. What it deliberately does NOT carry, and why:

- `Region.restoration` mid-ease values — animation, not progress; load snaps to `restore_to`.
- The per-tile fog `reveal` (45 KB of float) — rebuilt on load as one instant of standing at the
  saved position, the exact taper `reveal_around` converges to. Tiles explored long ago and now
  far away re-fog; that loss is honest and noted in the phase doc.
- Render-only state: facing, walk cycle, camera, clock.

Loading regenerates the world from the saved seed through the existing `game_init` — never a
second load path that could drift — then replays the deltas through `apply_restore`, which was
split out of `try_restore` so play and load share one definition of "restored". The whole file is
validated before the live game is touched, the world is regenerated into a heap scratch `Game`,
the saved position is checked against the regenerated solid map (`player_blocked`), and only then
copied over — a corrupt file cannot leave a half-loaded state. This is the first boundary where
outside input reaches the program, and it was treated as such: five distinct rejection paths, each
with its own negative control.

Keys: **F5** save, **F9** load, feedback in the title bar until the next keypress. The file is
`wayfarer.sav` in the working directory — fine for a contest entry run from its own folder; the
Program Files case is named in the phase doc rather than solved.

## Verification

`--save-test` (new): save → trash the live state → load → the restored state must be BIT-identical
to the snapshot taken at save time (seed, position, abilities, both counters, every restored flag,
every shard tile, every region's restore_to and restoration). Plus determinism (two loads of one
file agree) and five negative controls — truncated, wrong version, bad magic, out-of-bounds
position, missing file — each required to reject AND leave the live game bit-for-bit untouched.
