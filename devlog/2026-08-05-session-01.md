**[[Phase 03 - Legibility Tools]] — a bitmap font, and the live tuning overlay built on it.**

This phase exists because of how the last one went. Session 03's fog rewrite took three
edit-rebuild-screenshot passes to settle two constants, and the third pass only found the real
problem — stone had drifted too light in an earlier commit and was fighting the fog fix — because

ahead (water, paths, the player character, the restoration rebuild), and it is expensive in session
time even though it is free in bytes.

---

## Slice 1 — the bitmap font

5×7, bit-packed into a flat `static const Uint8` array, covering `0x20`–`0x5F`: uppercase, digits
and punctuation. No lowercase, deliberately — [[Found Souls]] specifies a single restoration line
and a tuning HUD is all-caps anyway, so the charset was sized against what actually has to be
displayed rather than built out to full ASCII on principle.

Hand-rolled rather than a sprite, per decision 3 in [[Handover]] §6: no `SDL_ttf`, ever. Three
functions next to the other graphics primitives — `draw_glyph`, `draw_text`, and `draw_text_shadow`,
which lays the string down in black one font-pixel down-right before drawing it in colour. That
shadow is what makes text legible over arbitrary terrain without a backing panel.

### The array is flat, and that is the point

`FONT_5X7` is indexed `idx * stride + row` with the stride passed in, rather than declared as
`[glyph][row]`. That exposes the stride as a seam **so the negative control can corrupt it.** A
2D array would have made the off-by-one impossible to express, and an impossible-to-express fault
is one the checker never proves it can catch.

### `--font-test`, with a negative control

Renders the whole charset through the real public API (`draw_text_shadow`, the path a HUD would
actually call) and counts lit pixels against a reference taken **straight from `FONT_5X7`** — not
from a second rendering pass, and not hardcoded. Then renders the same glyphs with the stride off
by one and requires the count to *differ*.

Two things this got right by accident of construction, both worth keeping:

- **The reference tracks the table.** Adding `<`, `=` and `>` mid-session moved the expected count
  from 2,236 to 2,316 with no test edit. A hardcoded number would have needed hand-updating, which
  is exactly how a checker quietly stops checking.
- **The first run failed, correctly.** Expected 559, rendered 2,236 — precisely 4×, because
  `FONT_SCALE` is 2 and each font pixel is a 2×2 block on the canvas. The checker was right and the
  expectation was wrong. Fixed by scaling the reference, and by counting exactly `white` rather than
  non-zero so `draw_text_shadow`'s black underlay stays out of the number.

## Slice 2 — the live tuning overlay (F3)

`TAB` cycles rows, `-` and `=` adjust, `F3` hides. **Not the arrow keys**, because arrows are
movement and the entire point is to tune while walking around — an overlay that steals the keys
which put you in front of the thing you are judging is not a tuning tool.

### Scope was a decision, not an omission

The phase file flagged "should these constants become runtime variables?" as a real architectural
question to settle explicitly. Reading how each one is actually used showed a genuine three-way
split rather than one uniform answer:

| Constant | Where it lives | Live-adjustable? |
|---|---|---|
| `FOG_TINT_R/G/B`, `FOG_KEEP` | `fog_lerp` only | **Yes** — next frame, no side effects |
| `SIGHT_MAX` | `reveal_around` | Partly — reveal only ever *grows*, so lowering it leaves walked ground stale |
| `LAND_ROCK_T`, `VILLAGE_*` | `world_gen`, `place_buildings` | No — needs a full `game_init` per keypress |

Put to the user, who chose **fog/colour only**. That is the cheapest option and it is also the one
that fixes the actual pain: every constant that thrashed in Session 03 was render-only. The
generation constants were considered and left out on the record, so a later session does not
rediscover the question from scratch — they already have `R`, and re-running the reachability
verifier on every keypress is a different tool from this one.

### How the +0-byte guarantee is kept

`fog_lerp` now reads `FOG_R_V`/`FOG_G_V`/`FOG_B_V`/`FOG_K_V`. Under `WAYFARER_SELFTEST` those
expand to fields of a `FogTune` struct; otherwise they expand straight back to the original
literals. The shipping build's generated code is therefore identical to having no overlay at all —
the same structural argument as `WAYFARER_PERF` (decision 8), which is what makes the byte claim
trustworthy without re-deriving it each time.

### Two glyphs missing, found by looking

The first overlay screenshot rendered its own help line as `TAB ROW  -  ADJUST` — `=` (0x3D) was
inside an "unused" run of zeros. So was `>` (0x3E), which meant the selected-row cursor was
invisible and the row was distinguished by colour alone. Both added.

**Every test was green while this was broken.** `--font-test` counts pixels against the table, so a
glyph that is blank in the table is blank in the reference too and the counts agree perfectly. The
test verifies the renderer draws what the table says; it cannot verify the table says the right
thing. That needed a screenshot, which is the same lesson Session 02 learned about lollipop trees
and ziggurat roofs.

## Session 02 — the world was too big, and W finally points up

Systems touched: [[Isometric Rendering]] · [[Art Bible]] · [[Phase 04 - Traversal]]

The user closed Phase 03 by running the self-test build — *"everything works so far in self test
run"* — which discharges its human-usability gate. Then: **"increase the tile density with
decreasing the assets size. Right now everything seems too big."**

### Why everything was too big, precisely

Every prop, building part and elevation step in `src/main.c` was hand-authored in **absolute pixels
against `TILE == 32`**. That made `TILE` a lie. The projection identity genuinely holds at any tile
size — that part of [[Isometric Rendering]] was true — but changing `TILE` left a tree the same
30 px tall while the ground under it shrank. Props therefore grew *relative* to the world.

Concretely: a canopy was 22–31 px wide on a 64 px diamond, and a tree stood 29–44 px tall against a
tile only 32 px deep. Houses were worse — a 3×3 footprint drew a 202 px roof. The screenshot showed
two enormous plates in a field of oversized lollipops, with the player a speck between them.

### The fix: make `TILE` honest

New `PX(n)` / `PXF(n)` — "n pixels, as authored at a 32 px tile" — wrapped around every authored
dimension. `TILE` is now **one knob for the whole visual scale**: trees, houses, cliffs, player,
reach ring, entity markers and surface marks all scale together and keep their proportions to each
other and to the ground. It rounds to nearest rather than truncating, so a 1 px detail line does
not quietly become 0 px and delete itself.

Then `TILE` 32 → 24, and the world **80×45 → 108×60**, chosen so the island keeps its extent in
world pixels (2592×1440 against 2560×1440) and is simply sampled 1.8× more finely. That works
because `land_noise` reads **normalised** coordinates over fixed-size lattices, so the island's
*shape* is resolution-independent — the same island, more tiles in it.

Net effect: 1.78× more tiles visible on screen, every asset smaller, island unchanged.

**A real bug this exposed:** `tile_detail` inset its marks to "4..27 of the tile's 32 px", which
overflows a 24 px tile — marks would have straddled the diamond edge. `PX()` now wraps the whole
offset, not just its constant. Nothing caught this but reading the code while changing it.

Tile-denominated constants had to be re-derived by hand, since they do *not* scale with tile size:
`REVEAL_TILES` 5 → 7 (keeps the sight circle ~160 world px), `VILLAGE_RADIUS`/`SPACING` × 32/24 (a
village keeps its physical size rather than shrinking with its tiles), `VILLAGE_SITES` 3 → 4 and
`BUILDING_TARGET` 15 → 22 (3 villages in a 1.8× larger world read as an empty island).

**690,176 bytes, −512.** The rescale *saved* bytes — `PX()` folds to compile-time constants.
Render 0.824 ms, unchanged from 0.821 ms, despite **37% more draw calls** (99,556 vs 72,445): the
same screen area, drawn as more, smaller tiles.

### Then Phase 04 — [[Phase 04 - Traversal]]

`W` moved up-*right*. `sim_step` fed keys straight into world axes, but world +x projects to screen
down-right, so every intention was rotated 45°. Open since before the isometric pivot, deferred
because it rewrites every trajectory in the simulation.

Rotated through the inverse of the projection's basis — screen-right is world (+1,−1), screen-down
is world (+1,+1) — then normalised by the vector's **actual** length (√2 for a screen axis, 2 for a
screen diagonal). The old code special-cased 0.7071 on diagonals only; doing it properly makes
speed direction-independent across all 8 directions rather than the 2 that happened to be covered.

`move_axis` was not touched. It resolves a world velocity into collision-respecting motion and has
no opinion about where that velocity came from — which is exactly why swept-AABB collision and wall
sliding are unchanged, and why that was the right seam to leave alone.

### The livelock, which is the real story of this phase

The phase file predicted the autopilot would need rotating too. It did. What it did not predict is
that **rotating it the obvious way deadlocks the playthrough entirely.**

Rotating the raw world deltas and thresholding afterwards means `ddx=+0.5, ddy=−0.5` — comfortably
inside the rest zone on *both* world axes — rotates to `sdx = 1.0`, which clears the 0.6 threshold.
The autopilot twitched where it used to sit still, overshot by a full 2.75 px step, and oscillated
between two tiles forever. **3 of 3 seeds hit the 200,000-step cap having restored 0–4 of 19.**

It presented as a hang, not a failure: 200,000 steps × two BFS passes over 6,480 tiles is minutes
per seed, so `--play-test --seeds 50` simply stopped returning. The 5-seed run with verbose output
is what turned it from "something is slow" into "the autopilot is stuck".

Fixed by applying the deadband **first, in world space**, and rotating only the resulting −1/0/+1
intent — the rest condition is then identical to before the phase. Steps per seed went from 200,000
(capped) to 2,676–3,441.

Worth generalising: **when you rotate a control signal, rotate the decision, not the measurement.**
A threshold is a judgement about the space the target lives in.

### The test had to be rewritten, not just re-run

`speed_selftest` measured world-x displacement under `in.right`. That only worked while input was
world-aligned — a *correct* screen-aligned simulation would report 0.707 of the speed and "fail".

The invariant was never about axes. It is that travel **distance** per unit time does not depend on
direction, which is basis-independent and would survive another change of orientation without being
rewritten again. It now checks all 8 directions, and additionally checks each one ends up where the
screen says it should — the part that would have caught the original up-right bug.

It also gained the negative control it never had: `input_negative_test` replays the **old**
world-aligned mapping and requires the direction check to reject it, 4 of 4 caught. Without it,
"screen dir correct" on all 8 would prove only that the checker agrees with the code.

### Camera

Deadzone plus an exponential ease on the excess. Kept in floats because at integer precision a
sub-pixel remainder truncates to no motion and the camera stalls short of its target forever. The
deadzone is asymmetric — y halved — because the projection compresses screen y 2:1, so an
equal-pixel box would feel twice as loose vertically. `cam_ready` makes the first frame of a world
snap rather than slide in from the corner.

The band-sweep cull reads the live `cam_y`, so camera lag does not break it, and the existing
player-clamp already covered the corner case the phase file flagged.

## Session 03 — the houses were a mess, and the rule debt is paid

Systems touched: [[Isometric Rendering]] · [[Village Generation]] · [[Phase 05 - Verification Debt]]

The user's verdict on the rescaled world: *"the houses have wrong size and wrong geometry, it's a
mess overall."* Right on all three counts, and all three had been true since buildings landed.

### 1. The roof was half a tile below its own walls

`draw_building` carried `cy -= cam_y - ISO_HH`. That `ISO_HH` was pure error.

`iso_tile` takes `ax` as the diamond's **centre** — it does `x0 = ax - ISO_HW` internally — with
its top vertex at `ay`. So a tile's visual centre is exactly `(ax, ay + ISO_HH)`, which is
*precisely* what `world_to_iso` returns for that tile's centre point. **Projection and rasteriser
already agree.** That is why props, entities and the player need no correction anywhere, and the
roof's extra `ISO_HH` simply pushed every roof half a tile down the screen, exposing the wall's
pale top face along the up-left edges. That band is what read as "the roof has slid off".

**I got this wrong once on the way**, and it is worth recording: I assumed `ax` was the diamond's
*left* edge and added a compensating `+ISO_HW`, which doubled the offset in the other direction.
The screenshot caught it in one round trip — but reading the six lines of `iso_tile` first would
have been faster than guessing at its anchor.

### 2. The windows were drawn on the roof

The facade hung off `cy - wall + ISO_HH` — a constant that only made sense *alongside the roof's
own error*. Fix the roof and the windows climb onto it. This is a general trap: **a visual constant
tuned against a buggy reference bakes the bug in**, and when the reference is fixed everything
measured from it has to be re-derived, not nudged back.

Re-derived from the wall-top diamond instead. At horizontal offset `ox` from centre, the top of the
wall is at `ftop + (fw - ox) / 2` on both front faces, and the wall runs straight down from there.
Everything hangs off that one line. `fw` is the footprint half-width *without* the eave — using
`rw` is what used to push details past the wall's corners.

Windows became one row **per storey** on both visible faces; a single row on a three-storey wall
read as a warehouse with one porthole. The door now stands on the ground line rather than floating,
and the ground floor of the right face skips its windows so the two never overlap.

### 3. The walls were too short for the footprint

A 3×3 footprint draws a 152 px roof. Over a 30 px wall that is a tent pitched on a kerb.
`STOREY_H` and `WALL_BASE` roughly doubled, so a storey comes to about one tile-depth of screen
height — the unit the eye already uses to judge scale everywhere else in the scene. This was only
*visible* once defect 1 was fixed and the real proportions could be seen.

All three are render-only, so the suite was re-run rather than re-argued. **691,200 bytes, +512.**

### Then [[Phase 05 - Verification Debt]] — `4847bf5`, +0 bytes

`--fog-test` asserts the two properties Phase 02 needed and never measured. **Separability**:
adjacent shades within a palette ramp must still differ at reveal 0 — the "a four-shade canopy must
not become one blob" property `FOG_KEEP` exists for. **Ordering**: if A is lighter than B at full
colour it must not come out darker at any reveal level. 45 real palette colours × 5 reveal levels:
0 inversions, 0 collapsed ramps, 3 collapses (ties under rounding, reported not failed).

Colours come from `canopy_pal`, `rock_pal` and `terrain_colour` rather than convenient synthetic
values — the phase file's trap warned that far-apart test colours pass trivially without ever
exercising the near-adjacent case rounding can reorder. The negative control replays a
contrast-crushing blend and both checks catch it: 14 collapsed ramps, 206 collapsed pairs.

`--land-test` bounds coverage, connectivity, ocean contiguity, rock coverage, and — an assumption
`place_buildings` had always made silently — that buildable ground exists at all.

### The finding, which is the reason the phase was worth doing

The obvious assertion, *the walkable landmass is one connected component*, **fails on 3 of 100
seeds**. Going and looking at those seeds is what made the phase pay:

The generator produces a **detached lobe across open water**. That is not a defect. Ocean is
`solid` and never walkable, so the lobe is unreachable by construction; `place_entities` only ever
places into regions reachable from the spawn, so nothing is stranded there; and all three seeds
still play to completion. **An unreachable islet on the horizon is a feature of an island game.**

What *would* be broken is the player spawning on a small lobe with the world across water. So the
assertion was re-aimed at the component the player actually spawns in, as a fraction of the whole
map — absolute, per the relative-assertions trap. Seed 16 is the worst case at 56% of open ground
and 17.8% of the map, and passes **on merit**, not because a bound was moved to admit it.

**Setting a threshold to make a test pass is the failure this project keeps warning about.** The
fix for a failing bound is to find out what the assertion is really asking, not to loosen it.

The negative control shatters the map into **four** quarters, not two. A two-way split leaves the
player reaching ~50% of open ground — right on the fragmentation bound, and a control that only
just fires is one that stops firing the first time somebody nudges a threshold.

## Session 04 — rivers reach the sea, and the chat hands over

Systems touched: [[World Generation]] · [[Isometric Rendering]] · [[Phase 06 - Water And Bridges]]

The user's verdict on the fixed houses: *"fine, not perfect but workable."* On the land: *"decent
but lacks the pixelated game feel."* Then a direct question — should they add PNG assets? — and
instructions to answer it and move on to the next phase.

### The asset answer, because it will be asked again

**Yes to PNGs, as bake *inputs*.** They are source files on a build machine and never ship.
`SDL_image` is compiled out and the zero-external-files rule is absolute, so nothing decodes a PNG
at runtime; the pipeline is PNG → build-time script → compiled-in C header → pixels.

A 32×32 sprite at 4 bpp bakes to 512 bytes against 747,776 free, so there is room for well over a
thousand. **Bytes are not the constraint. They never have been on this project.**

But the more useful half of the answer was that **assets are probably not what "pixelated game
feel" is missing.** The renderer draws 960×540 upscaled ×2 — a fine pixel grid, so the world reads
*smooth* rather than chunky. The cheap lever is dropping `LOGICAL_W`/`LOGICAL_H` to something like
640×360 at ×3, plus tighter palette discipline. Worth trying **before** anyone draws anything, or
the art gets authored against the wrong pixel density and has to be redrawn. Recorded as an open
decision in [[Handover]] §9.

### Rivers, and a trap designed out rather than handled

[[Phase 06 - Water And Bridges]] proposed steepest descent over the height field, and flagged its
own trap in the same file: a height field has local minima that are not the coast, so a descent can
wedge in a landlocked dip and needs a policy for it.

Rivers instead descend a **multi-source BFS distance-to-SEA field**. Every tile with a finite BFS
distance has a neighbour exactly one closer, *by construction* — so a walk that always steps to
`dist - 1` strictly decreases and must terminate at water. There is no "what if it gets stuck"
branch because there is no stuck state. Meander comes free from picking randomly among the
equally-good candidates, of which there are usually several.

That is the more satisfying kind of fix: not handling the failure mode, but choosing a field where
it cannot occur.

### Bridges are not a collision special case

The phase's task 3 asked for one line in `tile_blocked` returning not-blocked on a bridge tile.
**That was not done, deliberately.**

Making collision read a second signal means `bfs_open`, `flood_open`, `regions_build` and
`walk_regions` all have to learn about bridges too — or walk-reachable and graph-reachable disagree
and `--gating-test` is right to fail. A bridge instead simply **clears `solid`**. Collision, the
region graph, the reachability verifier and the autopilot then all see a crossable tile through the
code path they already used, and `bridge[][]` exists only so the renderer can draw planks.

**The phase adds zero new inputs to collision** — stronger than the "exactly one" its own trap
section was willing to allow, and decision 12 survives untouched. Rivers and bridges both land
before the verifier, exactly as buildings do, so a river that seals a region off with no crossing
is rejected and regenerated by machinery that already exists.

### Bridges are load-bearing, and now it is measured

The phase file called this its single most important test, and four handovers carried it as the
highest-value item left in the project. `--bridge-test` regenerates each seed twice — once normally,
once with `g_suppress_bridges` skipping the decking step — and compares the size of the open
component the player spawns in, which is `game_init`'s return value and the same metric
`--land-test`'s shattered-island control already uses. Both runs share a seed, and decking draws no
RNG, so nothing upstream of it can diverge between them.

**200 of 200 bridge-bearing seeds shrank when suppressed.** A bridge is the thing reconnecting a cut
island on every seed measured, not decoration.

Worth naming what this control *is*, because it is shaped differently from every other one here.
The others build a broken world and confirm a checker rejects it. There is no such construction for
bridges: the flood fill is exact, not a fallible checker, and cannot pass when it shouldn't. What is
being verified is the **empirical claim**, so the test fails only if it never once observes a
shrink across the sweep. Same "a check that has never rejected anything proves nothing" bar, applied
to a measurement instead of a checker.

The honest limit: this measures reachable-area *shrinkage*, not solvability. The stronger claim —
"the verifier would reject this seed outright without its bridge" — is not what is checked, because
entity placement re-runs against the smaller component and can still succeed. Shrinkage is what is
measured and shrinkage is what is reported.

### Waterfalls, and getting the direction backwards

The blocker the last session named was real and the fix it proposed was right: `world_heights`' local
`dist` is the chamfer distance *into solid masses*, which is 1 along a one-tile-wide river, so there
was no gradient to terrace with. `World` now carries `sea_dist[][]`, the BFS field `place_rivers`
already computed and then threw away — render-only, ~6.5 KB of a stack-local `World`, zero exe
bytes. `world_heights` quantises it into steps, each step is a real height delta between adjacent
tiles, and `iso_tile` draws the water-coloured side face by itself. **No new rasteriser routine**,
so the phase's trap about recolouring cliff-face code never came up.

What the handover did not anticipate is that **the descent has to be depth, not elevation.** The
first attempt terraced upward going inland, which is the obvious reading of "steps down to the
coast" — but the land a river cuts through sits at height 0, so the bed clamped to ground level
within two steps and the river stopped being a channel at all. It rendered as a blue path painted on
the grass: strictly worse than the flat version it replaced. The working form is shallow at the
source stepping **down** to the sea, with the deepest step landing exactly on the sea floor's own
deepest step so a mouth meets the shelf instead of dropping past it.

Then a second fault the first one hid: **a bridge deck drew at the bottom of the channel.** A bridge
tile is still `SURF_RIVER` — that is what keeps the water reading as continuous under it — so it had
always taken the river's height branch. Invisible while the river was one flat shallow depth; a
walkable pit the moment it wasn't. It now takes ground level, checked *before* the river branch.

Neither fault is testable. `height` is render-only by construction, so no checker in this project
can see either one, and both were found by screenshot — the same lesson as the lollipop trees, the
ziggurat roofs, and the roof half a tile off its own walls.

### Probe the data for existence, screenshot for judgement

`RIVER_FALL_EVERY` started at 8 hops per step and was wrong: rivers reached only 2–3 of their 4
steps, because sources sampled at `RIVER_SRC_MIN` land around 15–25 hops out, so the whole channel
sat at the deep end with no shallow headwater to fall from. That showed up instantly in a throwaway
probe that printed each river's distinct bed heights, and not at all by eye — a 3 px step is right
at the edge of what a capture settles. At 5 hops, seeds 3/5/7/12 show 3–4 distinct levels.

The general form, which cost a couple of rounds of squinting before it was obvious: **probe the data
to find out whether a feature exists; use the screenshot to judge whether it is any good.**

### Verification

Re-**run**, not re-argued, after both changes: bridge 200/200, land 30/30 with both controls, reach
50/50 with its control, gating 30/30, **play 50/50**, iso PASS. Release build +0 bytes, zero
warnings under `-Wall -Wextra`.

### NOT verified

- **The waterfall drops are 3 px and nobody has judged them.** The staircase is confirmed in the
  height field and the channel now reads as a channel with banks, but whether a 3 px step reads as
  *falling water* to a player is unjudged. [[Phase 10 - Motion]]'s shimmer is what would sell it;
  until then this is geometry that is correct rather than an effect that is convincing.
- **Rivers have now been seen on four seeds** (3, 5, 7, 12) rather than one. Still no sweep of
  whether they are scenic or arrow-straight, whether two can merge into a lake, or how often one
  forces a detour.
- `--land-test` still knows nothing about `SURF_RIVER` or bridges.
- Everything unverified at the end of Session 04 still is: camera feel, `TILE` 24, pacing, the
  "pixelated game feel" question, audio, and the fact that one playtest is not QA.

**Phase 06 is done. Next is [[Phase 07 - Asset Seam]]** — the build-time PNG→`src/assets.h` bake,

## Session 06 — the team's art arrives, and the seam it goes through

Systems touched: [[Isometric Rendering]] · [[Art Bible]] · [[Phase 07 - Asset Seam]]

An untracked `assets/` had appeared at the end of the last session: 130 PNGs from the teammates,
plus 81 Godot `.import` sidecars. The user chose a full art pass over the safer thin slice, so this
session built the bake pipeline **and** ran the real art through it.

**`wayfarer.exe` 755,200 bytes, +62,976.** Zero warnings. Full suite green including play 50/50.

### Bytes finally mean something, and it is assets

Every line of game logic ever written for this project comes to about 23 KB. **37 sprites cost
62,976** — roughly 2.7x all of it. Still only 8% of the free space, and the other 93 sprites would
fit several times over, so the conclusion holds: bytes are not the constraint. But the *shape* is
worth knowing now. If anything ever threatens the limit it will be art, and the lever will be which
sprites get baked rather than how the game is written.

### The format spec did not survive contact with the art

[[Art Bible]] §8 specified indexed palettes of **≤16 entries**. Measured across the real set: 7–49
colours per sprite, mean 18, with **36 of 93 over 16**. 4 bpp was never an option. The format is
8-bit indices against a per-sprite palette with **no quantisation**, so every authored colour
survives — collapsing toward a shared table would have traded visible fidelity on pixel art for a
few KB nobody needs.

The bigger win was structural: **71% of the authored canvas is transparent**, so sprites are trimmed
to their opaque bounding box before encoding. That is the largest single saving *and* it makes the
anchor honest — a sprite padded with empty rows would otherwise float above its own feet.

### The trap this phase named, and I walked into anyway

The phase file says plainly that an RLE decoder is new code with a new class of off-by-one risk,
and that the round-trip must be written **before** the decoder is trusted with anything visual.

I wired the sprites first. A screenshot showed bushes rendering paler than their source, and the
next stretch went on suspecting a palette off-by-one. Then `--sprite-test` got written and proved
the decoder **pixel-exact** in a single run — and the real causes were mundane (a magenta base disc
authored into the bush, and fog doing exactly its job).

**When a phase file names a test to write first, write it first.** The cost of ignoring it is paid
in screenshot round trips, which are the slowest debugging loop this project has.

### Retuning art means retuning what was calibrated against the old art

`prop_at` put a tree on 22% of open tiles. That read as scattered woodland when a tree was a ~20 px
procedural blob. A baked tree is 64x96 — wider than a tile, four tile-heights tall — so the
identical density closed into a canopy that hid the terrain, the buildings and the player. Retuned
to 12.5%.

Nothing warns about this. Density is not a collision input, so no test has an opinion; it is
visible only on screen.

### A building sprite is the whole building

Walls were never drawn by `draw_building`: footprint tiles get a wall height from `world_heights`
and the tile rasteriser extrudes them, which *is* the wall. A sprite carries its own walls, so the
ground under it has to go flat — leaving the extrusion stood a 96 px cottage on a 42 px plinth.

`building_sprite_id()` is therefore consulted by `world_heights`, `tile_colour` **and**
`draw_building`, so there is one decision rather than three that can drift. Footprint tiles stay
`solid`, so collision and reachability never move.

One thing came out clean by design rather than luck: a `w*h` plot spans `(w+h)*TILE` screen px, so a
2x2 plot is exactly 96 px — exactly how wide the small-house sprites are. The team authored against
a 48 px diamond, which is the scale the renderer already used. **That also killed the "pixel
density is blocking" worry** I had raised at the start of the session: it was wrong, and the
arithmetic settled it in a minute.

### Absent or occluded?

The character was invisible in several captures. Rather than keep zooming, one build with props
skipped settled it: she renders perfectly, feet on the bridge deck, correct facing. The trees were
simply in front.

So the depth sort is right and there is no bug — but there **is** a design problem, and it is now
the top open item: a 96 px tree covers a 48 px character often enough that the player loses track of
herself. Thin the trees, scale them down, or fade props that cover the player. Not chosen yet.

### NOT verified

- **The player-occlusion problem is confirmed and unfixed.** Highest-value open item.
- **The bush sprite has a magenta base disc** authored into it that reads as a halo on grass. Left
  alone rather than silently repainted — it is the teammates' art and should go back to them.
- **Nobody has played this.** Every visual judgement here is from screenshots, including "the
  village reads as a village" and "the fog reveal looks better with real art".
- No test proves a sprite lands on the right tile in *world* terms — `--sprite-test` checks the
  anchor is bottom-centre of its own box, not that the call site passes the right screen point.
- Whether the `.import` sidecars should be committed at all is still undecided.

**Phases 00–07 are done, and 07 absorbed most of 09. Next: the occlusion decision, then
[[Phase 08 - Save Load]].** Audio is still a softsynth from zero and still the biggest risk.

## Session 07 — the pale apron, and eight specs from someone who actually looked at it

Systems touched: [[Isometric Rendering]] · [[Art Bible]] · [[Phase 07 - Asset Seam]]

First session driven by a list of defects from playing the build rather than from a phase file.
Eight specs, worked in order. **`wayfarer.exe` 756,224 bytes, +1,024.** Zero warnings. Full suite
green: land, play 50/50, gating, reach, village 80/80, river, sprite, iso, rng, fog, region, bridge
200/200.

### The pale apron was one bug wearing three coats of paint

Reported as "a pale area around the building the player cannot walk through". It was three separate
things stacked, and only fixing all three removes it:

1. **The footprint was rolled before the sprite was chosen.** `place_buildings` rolled a 2–3 × 2–3
   plot and `building_sprite_id` then picked a sprite to fit whatever came out. A 2×3 plot projects
   to a **120 px** diamond; the small-house sprites are **64–74 px**. So 20+ px of bare plot showed
   on every side, and — because footprints are `solid` — all of it blocked movement.
2. **That bare plot was painted `0x8f7d5e` packed earth**, a previous attempt to make the overhang
   read as a deliberate yard. It never did; it read as the pale slab in the report.
3. **The surface-detail pass treated it as rock.** `terr = solid ? -1 : ...` sent building tiles down
   the rock branch and speckled pale pebble strata over them.

The fix inverts the dependency: a **kind** is chosen first (`BKIND_HOUSE/LARGE/WINDMILL/MARKET`) and
`bld_kind_fp` sizes the footprint so the plot's diamond matches the sprite standing on it — 72 px for
houses and windmills, 96 for the large building, 48 for the stall. Slight *overhang* is then correct
(eaves stick out past walls you collide with); slight *underhang* was the bug. With the plot the
right size, the paint covering for it goes too — footprint tiles now draw plain ground via a new
`tile_show_terrain`, which borrows a neighbour's region because solid tiles carry `REGION_NONE` and
asking directly would paint grass in the middle of a Kindle region.

`--village-test` now asserts `b->w/b->h` equal `bld_kind_fp[b->kind]`, so the two cannot drift again.

### Population caps, and the one that is an equality

Windmills ≤ 2, houses + large ≤ 6, **stall == 1**. The stall is the interesting one: it is placed
*first*, because it is the only structure with a hard clearance requirement and it has to pick its
ground before the houses eat the open plots, and its clearance **relaxes** (5 → 2, then a whole-map
sweep at 1) rather than the stall being dropped. One stall is a guarantee the player can orient by,
so a cramped stall beats no stall. `VILLAGE_SITES` came down 4 → 2: four sites sharing six houses is
not four villages, it is four pairs of sheds.

### A clearance is only a clearance if everything respects it

`prop_at` now returns `PROP_NONE` inside any plot's ring — **checked before the `solid` branch**,
which had been seeding boulders on top of the buildings themselves. The stall's ring is 5 tiles, so
its forecourt stays open.

Then a screenshot showed a cottage two tiles from the awning. `plot_free` only asks whether the
*ground* is open, and by the time houses are placed the stall's forecourt **is** open ground — so it
was reserved against vegetation and against nothing else. `clear_of_market` fixes it, and the test
asserts it, because vegetation and buildings are placed by completely different code and "the stall
has room" has to be asked of both or it is only half true.

### The purple was two things, and one of them was ours to fix and one was not

`TERRAIN_DARK` (the Kindle gate) was `0x3b3350` — violet ground, which is not a colour ground comes
in. Recoloured to `0x25332c`, a lightless hollow: still much darker and flatter than the sage grass,
so the gate stays legible before you hold Kindle, but it reads as land. The speckle followed it.

The louder one was **the bush's magenta base disc** — 163 px of `#74305E`/`#944171` family under
every bush on the map, which at bush density reads as purple patches of *ground*. Session 06 found
this and **deliberately left it alone**: "it is the teammates' art and should go back to them."

**That decision is now reversed, and it should not pass silently.** The user asked for the purple
gone, so the plate is repainted to a green shadow ramp in **both** `assets/nature/bush_small_01.png`
and `src/art_data.h`'s palette entries 274–277 — the source too, so a future `tools/bake.ps1` run
reproduces it rather than resurrecting the magenta. Verified 163 px changed and **zero** collateral
by pixel-diffing against `git show HEAD:`. Entries 274–277 belong to `BUSH_SMALL_01` alone
(`pal_off` 259, `pal_n` 19; neighbours are `CHAR_PLAYER_W_3` at 242–258 and `GRASS_TUFT_01` at 278),
so nothing else could be tinted. **The teammates still need telling** — their source file in this
repo no longer matches what they delivered.

### The river test that failed for the right reason

"Make sure there is a river on the side of the map" → river 0's source now takes the **best** of 600
samples by distance from the centreline instead of the first valid one.

The first version of `--river-test` asked whether a river reached the outer third of `WORLD_W` and
**failed at 19/40**. The threshold was wrong, not the code: the island does not span the map, so most
of that outer third is open sea and no river could ever have reached it. Measuring a river against
ground that does not exist tells you about the coastline, not about the sampler. Rescored against
**the island's own extent**: 40/40, mean reach 74%.

Rescoring a failing test until it passes is exactly how a test gets hollowed out, so it carries a
negative control on the `g_suppress_bridges` pattern — same seeds, `g_suppress_river_bias` set:
**flank rate 100% → 35%, mean reach 74% → 43%.** The bias is load-bearing and measured to be.

- `--village-test` 80/80: footprints match their kind, caps hold, stall is exactly 1 on every seed,

- `--river-test` 40/40 with its negative control passing.
- Screenshots on ~15 seeds: no pale apron under any building, no purple ground, no purple bush
