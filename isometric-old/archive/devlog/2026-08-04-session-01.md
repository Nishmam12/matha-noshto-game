# 2026-08-04 — Session 01

Hub: [[Wayfarer MOC]] · Index: [[INDEX]] · Process: [[Agent Prompt]] · Plan: [[Overview]]
Previous session: [[2026-08-02-session-03]]

**Start of the isometric pivot.** The team asked for a 2.5D isometric pixel-art look with layered
procedural art and a village world, replacing the flat top-down coloured-square renderer. This is
a change of rendering approach, which [[Agent Prompt]] names explicitly as requiring a flagged
decision rather than autonomous action — it was raised, three options were put, and the largest
was chosen deliberately. See [[Isometric Rendering]] and [[Village Generation]].

The size question was answered before any code was written: **bytes are not the constraint.** The
exe is 679,424 bytes of which 669,696 is SDL2 — every line of game logic written across Weeks 1–3
totals **9,728 bytes**, about 3.6 bytes per source line at `-Os`. The whole renderer plan is
estimated at +7 to +16 KB against 760,576 bytes of headroom.

## Slice 0 — The measurement that never existed

### Why this came first

[[Toolchain Setup]] and [[Handover]] both list "render cost of the tile loop not profiled" under
NOT verified, and the only performance number on record was **"56.2 fps"** from
[[2026-08-02-session-01]]. That number was never evidence of anything. The loop sleeps on purpose
to cap the frame rate, and `SDL_Delay` has millisecond granularity — `Sleep(14)` routinely returns
at 15–16 ms on Windows. The measurement was of sleeping, not of drawing.

Changing the renderer against an unmeasured baseline would have meant no way to tell whether the
new one was expensive. So: measure first, change nothing.

### Change

Four separate stopwatches per frame — **render**, **present**, **sleep**, **whole frame** — plus
pixel and call counters incremented inside `fill_rect` after clipping, so the count is real writes
rather than requested ones. Reported live in the window title with `--perf` (the only text channel
that exists before the Week 5 bitmap font) and as a summary on exit.

All of it sits behind `WAYFARER_PERF`, which defaults to `WAYFARER_SELFTEST`. The shipping binary
therefore contains **no** measurement code at all — the same structural argument as decision 8 in
[[Handover]]: "no debug code in the submission" should be a property of the build, not something
somebody has to remember. Both binaries run the identical render path, so numbers measured in one
apply to the other.

### Measured — 600 frames, seed 3, 640×360

```
render   mean   0.110 ms    max   0.341 ms
present  mean   0.127 ms
sleep    mean  16.534 ms    <- frame cap; SDL_Delay granularity lands here
frame    mean  16.851 ms    = 59.3 fps
pixels   mean    230544 /frame  = 1.00x the 230400-px screen
calls    mean       947 /frame
```

### What this settles

- **The "56 fps" was sleep, confirmed.** 16.534 ms of a 16.851 ms frame — **98.1%** — is spent
  inside `SDL_Delay`. The renderer was never the limiter and never came close to being it.
- **Render costs 0.110 ms of a 16.67 ms budget: 0.66%.** There is roughly **150× headroom** on the
  render path. The isometric renderer is projected at ~5.7× the pixel traffic of this one, which
  lands near 0.6 ms — still under 4% of budget. Performance is not a reason to compromise the look.
- **`pixels = 1.00× the screen` proves the flat loop has essentially zero overdraw**, which is why
  it never needed a screen clear. That property does not survive the isometric change: diamonds
  only tile the plane where the world exists, so a clear becomes mandatory in slice 1.
- **947 calls/frame** against ~1008 visible tiles — the difference is edge tiles clipped away.

### Not verified

- Measured on one machine, with the window unoccluded. `present` in particular is an OS blit whose
  cost depends on the compositor and window state; the 0.127 ms figure should not be treated as
  portable. It is a baseline for *comparison against later slices on this box*, which is what it is
  for.
- `--input-test` runs and reports cleanly, but with no external driver it sees no keys
  (`up=0 down=0 left=0 right=0`) and reports a zero position delta. Exercising the real key path
  needs the `PostMessage` harness described in [[Handover]]; that gets set up in the slice where
  input actually changes.

is the strongest available evidence that the instrumentation is genuinely absent from it.
Self-test build 696,832 bytes (not a deliverable, not budget-tracked).

## Slice 1 — 32 px tiles and the isometric projection

### The transform, and why the tile size was free

Choosing `ISO_HW == TILE` and `ISO_HH == TILE/2` collapses world-to-screen to

```
sx = wx - wy + ISO_OX
sy = (wx + wy) / 2 + ISO_OY
```

one subtract and one halve, no multiplies, no matrix, exact on integers. The identity depends
only on that ratio, so it holds at any tile size — which is why raising `TILE` from 16 to 32 in
the same slice cost nothing here.

### The rasteriser, and why it is provably gap-free

One new primitive pair, `vspan` and `iso_tile`, drawing **per screen column** rather than per
scanline. For column `i`, with `a = |i - ISO_HW|`, the top face starts at `a>>1` and runs
`DIA_H - a`. That is the *exact preimage of the tile under the inverse projection*, not a slope
walk — which is what makes the tiling provably exact rather than hopefully exact. For the east
neighbour `a_A + a_B = DIA_W/2`, and requiring A's bottom edge to meet B's top reduces to an
identity holding for both parities of `a`. Elevation then costs nothing extra: raising a tile by
`h` leaves a hole exactly `h` tall starting exactly where the top face ended, so the side face is
**the same column immediately below**. There is no second edge computation that could disagree
with the first, which is the usual source of isometric seams.

A scanline diamond would have needed a separate parallelogram routine whose upper edge had to
agree to the pixel with the diamond's lower edge. That is precisely the seam bug class, so this
approach was chosen for correctness, not speed.

### Consequences

- **A screen clear became mandatory.** Slice 0 measured the flat loop at exactly 1.00× the screen
  — it covered every pixel by construction. Diamonds only tile the plane where the world exists.
- **The scale change is behaviourally neutral.** `player_blocked` divides by `TILE`, so doubling
  both the player box and the tile cancels exactly. Every sim test passed unchanged, and
  `--move-test`'s speed assertion tracked automatically because it was derived from
  `PLAYER_SPEED` rather than hardcoded (110.00 → 220.00 px/60 ticks, straight and diagonal).

### New: `--iso-test`, headless, with a negative control

The single highest-risk claim in this whole change is that diamonds tile exactly. An argument is
not a check.

- **Case 1** asserts `covered == composite == N × 1024`. Both gaps *and* overdraw fail it — a
  renderer that filled gaps by overdrawing would fail just as loudly as one that left them.
- **Cases 2 and 3** use random elevation: zero interior-column gap pixels (seams), and zero
  pixels owned by anything but the nearest tile covering them (depth order).
- **Negative control**: injects a one-pixel vertical offset into half the tiles — the smallest
  error the exactness claim forbids. Rejected, 63,800 px vs 65,536.

Also added `--shot FILE` to the self-test build (`SDL_SaveBMP` on the final frame). Grabbing the
window from outside is unreliable here per [[Handover]]'s `SetForegroundWindow` trap, and every
remaining slice needs to be looked at.

### Size and perf

**680,448 bytes, +1,024.** Render 0.425 ms (noisy run — see below), 2.00× screen pixels, which is
the clear plus one screen of diamonds exactly as predicted.

## Slice 2 — Elevation

`Sint8 height[][]` added to `World`, derived once at the end of `game_init` by a two-pass chamfer
distance transform into the solid masses. Rock rises one terrace per ring of distance from open
ground, so a cliff edge gets a rounded rim instead of a slab wall and an isolated pillar stays
short. Water sinks 6 px; `TERRAIN_LEDGE` rises 16, which makes that gate legible *before* you have
Climb.

**It is derived and render-only by construction and by placement**: `tile_blocked` still reads
`solid` and `regions[].terrain` and nothing else, and `world_heights` runs after everything the
generator does. Nothing in movement, reachability, gating or the playthrough walker can observe
it — so the 50-seed completability proof needed re-*running*, not re-*arguing*. It passed
unchanged.

Lighting is two constants: the down-left face at 58% of true colour, the down-right at 76%. No
normals, no dot products. That is the whole model, and it is what turns flat colour into volume.

`objdump -h`: `.data` 17,520 B, `.bss` 2,912 B. The 3,600-byte array is inside `World` on the
stack — the `.data` trap did not fire.

**680,960 bytes, +512.** Render 0.275 ms ± 0.002 over four runs. Slice 1's 0.425 ms had a 2.124 ms
max, which marks it as a noisy run; the honest reading is that both sit near 2% of the 16.67 ms
budget.

## Slice 3 — 960×540 logical, integer-scaled into the window

The game now rasterises into a heap backbuffer and that image is integer-scaled into the window.
**The doubling is the point, not a shortcut**: a 1 px highlight on a trunk is a hairline at native
1080p and a visible 2 px band when drawn at 960×540 and scaled. That is the difference between
"procedural shapes" and "pixel art".

The backbuffer is `SDL_malloc`'d (2 MB of runtime memory, zero exe bytes) and wrapped with
`SDL_CreateRGBSurfaceWithFormatFrom` in the window's own pixel format, which `fog_lerp` needs for
`SDL_MapRGB`. If that fails the renderer draws straight into the window surface at native
resolution — a real degraded mode, since the renderer does not care what resolution it is handed.

### Two things the first attempt got wrong

1. **Scale detection.** Guessing 80 px of window chrome picked ×1 on this 2048×1152 display, where
   ×2 fits with 72 px to spare. Now it asks SDL for the *usable* bounds, which already exclude the
   taskbar, and only allows for the title bar. `--scale N` overrides; **F11** toggles borderless
   fullscreen, which on a display tall enough for the doubled image but not the chrome is the only
   way to get the intended pixel scale.
2. **Margins.** `blit_scale` is general over the integer factor and centres with the leftover
   margin cleared, rather than assuming an exact multiple. Fullscreen at 2048×1152 leaves a 64×36
   border that would otherwise hold whatever was in the surface before. Only the margins are
   cleared — ~285k px instead of 2.36M.

`present()` is shared by `main` and the autoplay harness and recomputes the scale from the live
surface each frame, so toggling fullscreen needs no special case. The backbuffer is allocated even
at scale 1: a path that only exists above a threshold is a path that only gets tested above one.

**`--iso-test` case 4** checks the scaler at ×1, ×2 and ×3 into a destination deliberately *not* a
multiple of the source — the fullscreen case where a centring or margin bug would live. Every
source pixel must become exactly its own s×s block in the right place, and every margin pixel must
be *cleared* rather than left stale (the destination is pre-dirtied with 0xAB to catch that). Zero
wrong pixels and zero stale pixels at all three scales.

**682,496 bytes, +1,536.** At ×2: render 0.590 ms, present 1.246 ms, 3.18 M px/frame — ~11% of
budget. Render is unchanged by the scale, as it must be; only present moves.

## Surface detail — per-tile hash, ground grain, terrain marks

`tile_hash` is a stateless SplitMix64 finaliser over `(seed, tx, ty)`, **deliberately not drawn
from the terrain or entity RNG streams**. Decoration therefore cannot perturb a single fragment
placement, and every existing seed-based result stays valid *by construction* rather than by
tracing the call graph to prove it. It is also stable regardless of draw order or culling, so
nothing crawls or flickers as the camera moves. The bit budget is documented once at the
definition so it is never re-derived.

Two layers:

- **Grain**, a two-tone dither over the top face, indexed by `(i ^ a>>1)` so the pattern follows
  the tile's own diagonal axes and reads as ground in perspective rather than screen-aligned
  noise. The first attempt used one bit per screen column and produced visible **vertical
  stripes** — a whole 32 px column took a single shade. Splitting each column into two
  independently-indexed halves breaks the streak for one extra `vspan`.
- **Marks**, positioned by their offset *within* the tile in world pixels and then projected, so
  they land inside the diamond by construction and need no shape test or clipping. Rock gets
  pebbles and cracks, ledges get long horizontal strata that emphasise the shelf, grass gets six
  light and five dark tufts — one shade of speckle reads as dirt on a flat field, two read as
  depth in the grass.

**683,008 bytes, +512.** Calls nearly doubled to 72,812/frame for 0.2 ms.

## Layered trees and bushes, and a real depth sort

**This is the slice the isometric change was for**, and it is the technique the team specifically
asked for: build a tree from a trunk drawn in several shades and a canopy drawn in several shades,
stacked, with per-instance variation.

A tree is a trunk in 3 shades under a canopy of 6 overlapping lobes in 4 shades, every dimension
jittered from a different bit field of the tile hash. Nothing is a sprite; nothing is stored per
tile. The point is combinatorial:

```
8 canopy palettes × 4 trunk palettes × 4 trunk heights
  × 4 canopy widths × 4 canopy heights × 4 leans   = 8,192 distinct trees
```

from ~130 bytes of palette data and about forty lines. **Eight palettes is enough because the eye
reads silhouette before colour** — the shape jitter does the work, and the palettes only have to
stop the wood being a monoculture. The set includes two autumn ranges, a blue-green and a
near-black conifer.

### Two proportion fixes, both found by looking at the render

- Five barely-touching lobes read as **a stack of discs**. Six lobes, each drawn taller than its
  step so they overlap into one silhouette.
- An 11–17 px trunk under a 20 px canopy made every tree a **lollipop**. Trunk is now 7–13 and the
  crown starts low, the way a deciduous tree actually does.

### Depth sorting is now real

The band sweep gained a second sub-pass: ground for the whole band, then props for the same band,
then entities in that band, then the player if it is the player's band. The sub-passes have to be
separate because a prop is tall enough to spill onto the diamond of the tile to its *right*, which
is in the same band and whose ground would otherwise repaint over it.

The result: **a tree one tile in front of you occludes you and a tree one tile behind does not**,
with no z-buffer anywhere. `prop_at` additionally refuses to stand a tall prop where the tile in
front is ≥24 px higher — the one depth artefact a band sweep cannot fix, and three lines beat a
z-buffer.

**684,544 bytes, +1,536.** Props cost ~19k px/frame; render 0.752 ms, total ~2.1 ms of budget.

## Remaining props, and an isometric interact ring

Five more prop kinds built the same way as the trees — rock, reed, flower, crystal, stump — with
placement moved into a per-terrain switch in `prop_at`, so each terrain now has scenery that
identifies it at a glance rather than only by its flat colour. Boulders on cliff tops are
deliberately sparse: enough to break a bare plateau silhouette without turning it into scree.

Also replaced the interact ring. Four `fill_rect`s forming an axis-aligned box read, in an
isometric world, as a rectangle floating in the air. It is now a diamond outline at the player's
feet in the same 2:1 slope as the tiles, which reads as painted on the floor — which is what a
reach indicator is.

## Buildings — and how the village went in without breaking the guarantee

The plan called for replacing `world_gen` wholesale with a village generator. **That is not what
was built**, and the deviation was deliberate.

Buildings are stamped into the existing generator's open ground **before** the flood fill and the
reachability verifier. They are solid, so they genuinely change what is walkable — and a layout
that walls something off is rejected and regenerated by machinery that already exists. The
completability guarantee is *used as the safety net* rather than worked around, which is exactly
why it survived: 50/50 seeds still play to completion, and the reach test still passes all 50 with
its negative control intact.

### No wall-drawing code exists anywhere

Building tiles are solid; `world_heights` gives them a wall height instead of a rock height; the
existing tile rasteriser draws their front faces — which *is* the wall. That fell out of the
elevation slice for free and is the reason this work was small.

### Nine parts, not five prefabs

There are no building "types". Nine independent parts, each with 4–5 variations, are picked from
separate bit fields of one `variant` word:

```
wall material 5 × wall trim 4 × roof shape 5 × roof material 4 × door 4
  × windows 5 × chimney 4 × attachment 5 × sign 4   = 640,000 combinations
```

before footprint size and storey count multiply it further. Bigger footprints carry more storeys,
so a skyline has a few halls standing over the cottages.

### Two things the first render got wrong

- **The roof rise was a flat 5–7 px per step**, so every house read as an open-topped box with a
  plate balanced on it. In a 2:1 projection a 45° roof over a footprint of half-width `rw` rises
  exactly **`rw/2`** on screen. Deriving the rise from `rw` fixed it, with the shape variant
  choosing shallow / 45° / steep.
- **Three steps over a 130 px diamond is a ziggurat.** Seven reads as a slope.

Roofs are drawn **once** from the `Building` record at the footprint's front-most corner. Per-tile
would tear along every internal edge.

### Density

900 placement attempts gave a mean of **13** buildings per world, which reads as a hamlet. 3000
attempts gives **22**. Most attempts land on rock and are rejected cheaply; the strict plot test
(footprint plus a one-tile skirt, all open) is what keeps houses from fusing into cliffs.

### New `--village-test`, with two negative controls

The checks are **absolute, not relative** — [[Toolchain Setup]] records that every *relative*
region test once passed on a partition covering 5 of 1585 tiles, because they all compared counts
to counts. So this checks properties of the world itself: footprints are really solid, really
indexed to their own building, really disjoint, and really approachable. The controls inject a
non-solid footprint tile and a walled-in building, and confirm both are caught.

**689,152 bytes, +2,560.** Render 0.859 ms, present 1.259 ms — about 13% of the frame budget.

## A mistake worth recording

A PowerShell text round-trip (`Get-Content -Raw | Set-Content`) on `src/main.c` read the file as
CP1252 and rewrote it as UTF-8, turning all **76 em-dashes into mojibake and adding a BOM**. It
compiled fine, so nothing caught it until an editor edit failed to match its own `old_string`.
Both undone; the diff against the last clean commit is now only the intended changes.

**Rule: source edits go through the editor, never through shell text filters.** PowerShell 5.1's
`Get-Content` does not reliably detect BOM-less UTF-8, and `Set-Content -Encoding utf8` writes a
BOM. Together they silently corrupt every non-ASCII byte in the file.

## Session 02 — the landform, and a first honest look at it

Systems touched: [[World Generation]] · [[Isometric Rendering]] · new [[Art Bible]]

**Goal.** The previous session ended with "the world is still the cave generator, dressed." This
session took that seriously. It also did the thing three handovers in a row had deferred: **looked
at the screen**, using `--shot` on the self-test binary, before deciding anything.

### What looking at it actually showed

Four defects, none of which were visible from the test output — every test was green throughout:

1. **The landform was cave noise.** `world_heights` derives terrace height from distance into a
   solid mass, and the solid mass came from a cellular-automaton cave. So the *landform* was cave
   noise, and on screen it read as random brown lumps. There was no coastline anywhere.
2. **Unrevealed land renders as a dark blue-grey ~(58,61,69)**, and `SIGHT_MAX` caps walking-reveal
   at 0.42. About 95% of a 30x20-tile view is that one dead colour. This — not the camera — is what
   makes traversal feel closed-in.
3. **Texture is a two-tone dither plus <=5 one-pixel marks.** That is the whole surface system.
4. **`W` travels up-RIGHT.** Confirmed at the source: input drives world axes, and world +X projects
   to screen down-right.

### Slices

**Island generation.** Replaced the CA cave with a radial height field: `(1 - d)` plus two octaves
of smoothstepped value noise, thresholded at sea level, with a third lower-frequency octave raising
rock outcrops inland. Ocean and rock are both `solid`; which one a tile is lives in a new
render-only `surf[][]`.

**This did not touch a single collision input.** `solid` remains the only thing `tile_blocked`
reads, so the region partition, building placement and the 50-seed completability proof were all
re-*run* rather than re-*argued*. That property is worth more than it looks and it held.

**Village clustering.** Houses were placed uniformly over the whole island. The moment the landmass
grew, that put a building on nearly every open plot — a suburb of identical boxes with no ground
between them. Now: up to 3 village sites kept 22 tiles apart, plots drawn from two summed
rng_belows so they bunch toward a centre, footprints cut from 2..4 to 2..3 tiles, and the required
open skirt widened from one tile to two so there are lanes to walk down.

**Three visual fixes found only by looking:**

- *Slabs.* Every small outcrop got `dist == 1`, so every one came out as an identical flat-topped
  12 px platform — a lawn scattered with concrete. Fixed by making outcrops fewer and larger so the
  chamfer has room to make several terraces inside one mass, plus a small height jitter.
- *Checkerboard.* The first jitter was +-4 hashed per tile, so adjacent tiles disagreed every time
  and the rasteriser drew a step between all of them. Rehashed on the 2x2 block at +-2.
- *Broccoli.* Canopy lobes were **axis-aligned `fill_rect`s**. Six stacked rectangles are a stepped
  pyramid however their widths are chosen, and no palette work fixes a silhouette. Added
  `fill_ellipse` and a contact shadow — design/Art Bible.md §3, "everything touches the ground."

**Palette.** Grass off the saturated `0x4e9e54` onto a sage `0x3e5c35`; stone lightened so it is not
the darkest large surface on screen; water given a 4-step depth ramp; and **the two autumn canopy
palettes deleted** — at full reveal they read as autumn, at the 0.42 walking ever reaches they read
as dead, and a quarter of the wood was drawn in them.

## Session 03 — roof volume, and the fog rewrite

Systems touched: [[Isometric Rendering]] · [[Fog and Reveal]] · [[Art Bible]]

### THE FIRST HUMAN PLAYTEST HAPPENED

The `wayfarer.exe` holding the file lock at the end of Session 02 was **the user playing the game**.
Four consecutive handovers have carried "nobody has played it by hand" as a standing risk. That is
now false. Their verdict, verbatim: *"even though the gameplay is in early stage, it did feel
slightly enjoyable."*

That is one datapoint from the person who wrote the design, not a QA pass — [[QA Checklist]]'s "runs
clean on a machine without dev tools" is still unchecked and nobody outside the project has touched
it. But the specific risk "we have built something nobody has ever moved around in" is retired.

### Roofs

Diagnosed at the end of Session 02, fixed here. The roof is a stack of concentric `iso_diamond`s,
one flat colour per slice, so however the steps were shaded up the slope the whole thing read as a
plate — and an eave-shadow diamond tried in Session 02 made it worse, because a ring under a ring
is still rings.

Terrain does not have this problem: it gets its volume from `FACE_L`/`FACE_R`, one notional light
and two constants. Roofs now use the identical trick via a new `iso_diamond_lr`, which splits a
diamond down its vertical centre line into a down-left and a down-right slope at `ROOF_L`% and 100%.
Same column geometry as `iso_diamond`, so the two still line up exactly.

### Fog

The cause of "traversal feels suffocating", and it was never the camera.

`fog_lerp` scaled luminance to 0.55 and pulled it toward `(44,52,68)` — a **dark** blue-grey. Since
walking only ever reveals to `SIGHT_MAX`, about 95% of any screen was that one dead colour, and the
world read as a cave. Distance in the real world goes lighter, bluer and lower-contrast, never
darker ([[Art Bible]] §2).

Rewritten to pull toward a light cool haze while keeping a fixed fraction (`FOG_KEEP`) of the
source's own luminance contrast, rather than crushing it. Keeping the contrast is what stops a
four-shade canopy collapsing to one blob at low reveal. `SIGHT_MAX` 0.42 -> 0.50.

**This took three passes and the first two were wrong**, which is worth recording:

- `(86,100,122)` at `FOG_KEEP 0.42` — the cave became a washed-out uniform light grey. Overcorrected.
- Settled at `(60,70,86)` / `0.50`, but the stone ramp lightened in Session 02 then made outcrops
  the **brightest** large surface in the world; under fog they read as white shapes floating in a
  dark field and pulled the eye off the player. Stone pulled back to just above grass, per the value
  hierarchy the Art Bible specifies and the previous session did not follow.

`fog_lerp` remains the single path from true colour to screen colour, unchanged in that respect.
