## Slice 2 — Seeded PRNG with independent streams

### Goal

[[World Generation]] requires a custom PRNG with **independent** streams for terrain / entities /
audio, "so tuning one doesn't reshuffle another". The existing generator was a single xorshift32.

### Change

Replaced xorshift32 with **PCG32**. The reason is the independence requirement specifically:
PCG32's `inc` is a sequence selector, so each distinct odd value defines a different period-2^64
sequence. Seeding one generator per stream from a shared master seed gives streams that are
independent *by construction*. A single xorshift could only offer different offsets into one
shared sequence, which can silently overlap and would reintroduce exactly the coupling the design
forbids.

Added `rng_float`, `rng_bipolar`, and a rejection-sampled `rng_below` (naive `%` would bias
fragment placement toward low indices).

### Size

670,208 → 670,720 bytes (**+512**).

### Verified

`--rng-test`, across **23 seeds, all PASS**:

| Property | Result |
|---|---|
| Same seed → same sequence | identical over 100,000 draws |
| Different seed → diverges | 1000/1000 differ |
| **Terrain draws do not perturb entities** | identical |
| **Terrain draws do not perturb audio** | identical |
| Cross-stream value collisions | 0 / 100,000 |
| `rng_below(16)` worst bucket bias | 1.41%–3.33% across seeds (want < 5%) |
| `rng_bipolar` range / mean | [−0.99996, 0.99999], mean 0.00074 |

Audio was regression-tested after the swap since its noise generator changed underneath: tone
still 439.9 Hz, RMS 0.1414, callback worst case 0.074 ms, and seeded noise still reproduces
byte-identically.

## Slice 3 — Player movement + collision

Movement model resolved as **continuous** — see [[Open Decisions]].

### Change

- Tile world (80×45 @ 16 px = 1280×720), cellular-automaton cave, seeded from the terrain stream.
- Continuous float position, swept AABB resolved per-axis in ≤0.5 px steps so a fast player
  cannot tunnel through a wall, and sliding along walls still works.
- **Fixed 60 Hz simulation step** with an accumulator, clamped at 0.25 s so a window-drag stall
  cannot spin the catch-up loop. Movement is frame-rate independent and reproducible.
- Follow camera, clamped to world bounds.

### Two defects found and fixed during verification

**1. Sealed spawn pockets.** The first spawn rule picked the open tile nearest the middle. On
3 of 20 seeds that dropped the player into a one-tile pocket where they could travel ~3 px — the
reveal effect was untestable there. Replaced with a flood fill that spawns in the **largest** open
region. Every seed now has 562–1655 open tiles (15–45% of the world). The same fill is the
groundwork for Week 2's reachability invariant.

**2. Spawning against the world corner.** Using the region's lowest tile index put the player hard
against the top-left edge, where the camera clamps and most of the view is wasted. Now spawns on
the region tile nearest its centroid.

### Size

A third defect was found here that was worth more than both: **+41,984 bytes for this slice**,
which was far too much for the code involved. Section inspection showed `.bss` at only 2,912 bytes
while `.data` had grown to 57,200 — and `.data` is stored in the file. The map named the culprits:

| Symbol | Bytes |
|---|---:|
| `.data$game` | 18,016 |
| `.data$stack` | 14,400 |
| `.data$seen` | 3,616 |
| `.data$next` | 3,616 |

On PE/COFF, `-fdata-sections` emits zero-initialised statics as `.data$name` COMDATs rather than
`.bss`, so **~40 KB of literal zeros were being written into the executable**. Moving these
world-sized buffers from `static` to stack locals recovered **39,424 bytes** at no runtime cost.
Worth knowing before Week 2 enlarges the world — noted in [[Toolchain Setup]].

Net for the whole world + movement + collision system: **+2,560 bytes**.

### Verified

`--move-test`, **20 seeds, all PASS**:

- **Zero input → zero movement.** Added deliberately: it separates "a stray keypress moved the
  player" from "the simulation drifts on its own", which have very different fixes. It earned its
  place immediately — see the input note below.
- **Player never occupies a solid tile** on any step, in any of 8 directions, on any seed
  (0 overlaps across ~38,000 simulated steps per seed).
- **Never escapes the world border.**
- **Identical trajectory** from the same seed + input sequence.
- **Direction-independent speed**: straight 110.00 px / 60 ticks, diagonal 110.00 px. Without the
  0.707 factor diagonals would run 1.41× fast; verified in a deliberately empty world so walls
  could not mask it.

**Real input path**, verified in the actual binary via `--input-test`: holding **D** produced
`right=1` only and `dx +81.67, dy +0.00` — correct mapping, correct axis, no cross-axis leak.
Getting there took two attempts: `SetForegroundWindow` is blocked for background processes, so
synthetic keystrokes silently went elsewhere and the first attempt reported all keys up.
`PostMessage(WM_KEYDOWN)` straight to the window works. Distance is short of the nominal 165 px
because `PostMessage` key-hold timing is imprecise — not a movement defect; speed is verified
exactly in the headless test above.

## Slice 4 — First-pass fog-to-color reveal

### Change

Implements the blend [[Fog and Reveal]] specifies: `colour = lerp(drained grey, true colour,
restoration%)`. "Drained" is luminance pulled toward a cool fog tint and darkened, so unrestored
land keeps its **shape** but loses its **colour** — both halves of "shrouded in fog and drained
of colour".

Reveal rises toward a target that tapers with distance from the player, so the boundary is a soft
gradient rather than a visible disc.

**What is placeholder vs. real:** the blend maths and per-tile reveal field are the real thing.
Only the *trigger* is temporary — proximity now, fragment restoration later, at which point the
per-tile field becomes per-region restoration% that tiles inherit.

### Design note settled by the build

[[Fog and Reveal]] offered a choice between `SDL_LockTexture` and baked `SDL_Texture`s. Neither
exists in our build — SDL's render subsystem is compiled out entirely. Rendering is direct pixel
writes into the window surface. That note has been updated.

### Frame pacing

Removing the old `SDL_Delay(16)` left the render loop **completely uncapped** — 400 frames
finished almost instantly and the loop pegged a core. There is no vsync to fall back on
(`PRESENTVSYNC` went with the render subsystem). Added an explicit frame cap. Measured: 300 frames
in 5.34 s = **56.2 fps**. Slightly under 60 because `SDL_Delay` has millisecond granularity;
simulation is fixed-step so gameplay speed is unaffected.

### Verified

Captured from the live window with `PrintWindow`: soft radial gradient from blue-grey fog into
true green ground and brown rock, player centred, revealed trail persisting behind the player as
the camera scrolls. Screenshots at 2.5 s and after scripted movement both behave as designed.
