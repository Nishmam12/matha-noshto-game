# matha-noshto-game

A game that fits on a floppy disk.

Entry for the **2P Game Arcade "1.44MB Floppy Disk" contest**. Working title: **Wayfarer**.
Written in C99 against a custom, stripped-down static build of SDL2 — no engine, no runtime, no
asset files, no shipped DLLs. Everything you see and hear is generated by code.

| | |
|---|---|
| **Current executable** | **670,208 bytes** |
| Hard limit (floppy standard) | 1,474,560 bytes |
| Ship target (safety margin) | 1,440,000 bytes |
| **Headroom** | **769,792 bytes** |
| Status | Pipeline proven — window, software framebuffer and procedural audio all verified. Game design not yet finalised. |
| Deadline | 4 September 2026 |

> "1.44 MB" has three different definitions in common use. We build against the smallest
> (1,474,560 bytes) and target comfortably below it.

## Constraints

These are non-negotiable and checked continuously, not at the end:

- Final executable, fully decompressed and runnable, **≤ 1,474,560 bytes**
- **Standalone Windows executable** — no browser, no installer, no runtime dependency, no
  shipped DLLs beyond those Windows itself provides
- Runs **fully offline** with **zero external asset files** — no `.png`, `.wav`, `.ttf`,
  `.ogg`, `.mp3`. Graphics, fonts, music and sound effects are all generated at compile time
  or runtime
- Judged in this order: **finished → under size → fun**

## Quick start

Requires Windows and PowerShell. The toolchain lives **outside** the repo.

```powershell
# 1. Fetch the toolchain (defaults to G:\tools; override with $env:WAYFARER_TOOLS)
$TOOLS = 'G:\tools'
New-Item -ItemType Directory -Force $TOOLS | Out-Null

#    MinGW-w64 via w64devkit - self-extracting, no installer
Invoke-WebRequest 'https://github.com/skeeto/w64devkit/releases/download/v2.9.0/w64devkit-x64-2.9.0.7z.exe' -OutFile "$env:TEMP\w64devkit.exe"
Start-Process "$env:TEMP\w64devkit.exe" -ArgumentList '-y',"-o$TOOLS" -Wait

#    SDL2 source (we compile our own; see "Why we build SDL2 ourselves")
Invoke-WebRequest 'https://github.com/libsdl-org/SDL/releases/download/release-2.32.10/SDL2-2.32.10.zip' -OutFile "$env:TEMP\SDL2-src.zip"
Expand-Archive "$env:TEMP\SDL2-src.zip" -DestinationPath "$TOOLS\sdl2-src" -Force

# 2. Build the cut-down static SDL2 (once, ~1 minute)
.\build-sdl2.ps1

# 3. Build the game
.\build.ps1
```

`build.ps1` prints the exact byte size, the delta since the last build, and remaining headroom.
It **exits non-zero if the binary goes over budget**, so the size limit is enforced by the build
rather than by remembering to check.

```
BUILD OK   ...\build\wayfarer.exe
size       670,208 bytes
delta      +512 bytes (prev 669,696)
headroom   769,792 bytes under the 1,440,000 ship target
```

### Build options

| Command | Result |
|---|---|
| `.\build.ps1` | Shipping build → `build\wayfarer.exe` |
| `.\build.ps1 -Map` | Also emits `build\wayfarer.map` for size forensics (~1.5 MB) |
| `.\build.ps1 -SelfTest` | **Separate** `build\wayfarer-selftest.exe` with verification harness + console |
| `.\build-sdl2.ps1 -Clean` | Rebuild SDL2 from scratch |

The shipping binary contains **none** of the self-test code — it is a different binary built
with `-DWAYFARER_SELFTEST=1`, not a runtime flag. This makes "no debug code left enabled in the
submission" a structural guarantee rather than something to remember.

## Running it

```powershell
.\build\wayfarer.exe                  # ESC or close the window to quit
.\build\wayfarer.exe --frames 120     # run exactly 120 frames then exit 0 (for scripted checks)
.\build\wayfarer.exe --seed 12345     # seed the procedural generators
```

### Verification harness

```powershell
.\build.ps1 -SelfTest
.\build\wayfarer-selftest.exe --audio-test 3000                 # 3s audio, reports callback timing
.\build\wayfarer-selftest.exe --audio-test 3000 --dump out.f32  # dump raw float32 samples
.\build\wayfarer-selftest.exe --audio-test 600 --noise --seed 42 --dump a.f32
.\build\wayfarer-selftest.exe --audio-test 3000 --rate 44100    # exercise rate adaptation
```

Sample output:

```
obtained : 48000 Hz, format 0x8120, 2 ch, 1024 frames/cb
converted: no - device matched the request exactly
deadline       : 21.333 ms per callback
worst case     : 0.079 ms
headroom       : 0.4% of deadline used
partial writes : 0  (must be 0)
zero crossings : 17609 -> 440.0 Hz (expected 440.0)
```

Every procedural generator is seeded and replayable by design — `--seed N` reproduces any output
exactly, which is what makes a bad result debuggable instead of a ghost story.

## Why we build SDL2 ourselves

The official prebuilt MinGW `libSDL2.a` contributed **1,656,876 bytes** to a do-nothing
window — over the contest's hard limit before a single line of game code existed. Two causes:

1. It is compiled **without `-ffunction-sections`**, so the linker's `--gc-sections` can only
   discard whole object files, never individual unused functions.
2. It ships **every subsystem**: five render backends, the game-controller mapping database,
   HIDAPI, sensors, YUV conversion, a WAV loader.

`build-sdl2.ps1` recompiles SDL2 with `-Os -ffunction-sections -fdata-sections` and the unused
subsystems disabled:

| | Bytes |
|---|---:|
| Stock prebuilt `libSDL2.a` | 1,714,176 |
| **Our minimal SDL2** | **669,696** |
| Saved | **−1,044,480** |

The MinGW runtime was never the problem — a bare static `int main(){return 0;}` is 13,824 bytes.
Biggest single wins were `SDL_dynapi.o` (170,920 bytes of dynamic-dispatch table that a
statically linked binary can never use) and `SDL_gamecontroller.o` (116,708 bytes of mapping
strings).

Kept: `Atomic Audio Video Events Threads Timers Loadso`. Everything else is off. Consequently
**`SDL_Renderer` does not exist in this build** — drawing goes straight into the window surface,
which is the hand-rolled approach the project calls for anyway.

Full accounting, including ~250 KB of further reserve we have not spent, is in
[`design/Toolchain Setup.md`](design/Toolchain%20Setup.md).

## Engineering process

Work proceeds in verifiable loops: **plan → implement → build → measure → verify → report**.
A feature is not done until it has been compiled, run, and checked against a stated expectation.
Claims that cannot be verified (how audio *sounds*, how something *feels*) are recorded as
unverified rather than asserted.

Every session is logged in [`devlog/`](devlog/) with the exact build command, the resulting byte
size and delta, what was verified, and — importantly — **what was not**.
